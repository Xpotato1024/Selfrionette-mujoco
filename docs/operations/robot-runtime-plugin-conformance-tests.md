# Robot Runtime Plugin Conformance Tests

## Purpose

The conformance suite verifies that a production Robot Profile, Robot Runtime
Plugin, and MuJoCo model remain one explicit contract. It is a test-only
framework. It does not add runtime composition, registration, imports, or
public exports.

## Ownership split

`tests/support/robot_runtime_plugin_conformance.py` owns the immutable case
types, generic validation helpers, and common assertion order. It contains no
robot identity, model path, joint name, site name, or expected coordinate.

`tests/robots/<robot>_conformance_case.py` owns the production profile/plugin
selection, profile-owned model and configuration references, known qpos and
targets, expected numeric values, tolerances, and any model-aligned qpos or
endpoint adapter. Cases are registered explicitly in
`tests/robots/robot_runtime_plugin_conformance_cases.py`.

## Required case fields

Each case supplies:

- a unique case ID and expected profile ID;
- the canonical production profile and runtime plugin objects;
- the profile-owned model asset, home keyframe, endpoint site, and joint-limit
  configuration;
- canonical joint order and qpos/qvel dimensions;
- at least two known FK cases, two reachable IK -> FK cases, and two MuJoCo
  endpoint consistency cases;
- positive finite tolerances with units and coordinate frames;
- focused fail-closed probes for identity, model, endpoint, home, and
  configuration mismatches.

The generic suite does not assume four joints or equate joint count with `nq`
or `nv`. A future model with a different qpos layout supplies a case-owned
qpos application or feasibility adapter.

## Known values, frames, and tolerances

Known FK endpoints are literal evidence recorded before test execution. They
must not be generated by the FK solver under test, by IK followed by that FK,
or by a helper that delegates to the same implementation. Each value records
its provenance, unit, and coordinate frame.

IK -> FK is a consistency check and does not replace independent FK evidence.
MuJoCo endpoint cases load the real model, apply qpos through the existing safe
backend boundary, run `mj_forward` through the snapshot path, and compare the
plugin accessor with the declared site. A model-aligned evaluator is supplied
by the robot case only when an explicit frame adapter is required.

Tolerances are expressed in metres for endpoint comparisons. They must be
small enough to reject sign, axis, reference-angle, and frame mistakes. The
fast_arm IK tolerance is limited to the existing solver's `1e-5 m` convergence
contract; its model/site and known-FK checks use `1e-9 m`.

## Adding a robot

1. Define the case in `tests/robots/<robot>_conformance_case.py` using the
   canonical production profile and plugin.
2. Record known values independently and document their provenance.
3. Add the case explicitly to
   `ROBOT_RUNTIME_PLUGIN_CONFORMANCE_CASES`; do not use filesystem scanning,
   dynamic imports, entry points, or production registry mutation.
4. Run the focused case and the relevant Python suites.

The production robot profile/plugin registry remains the source of production
resolution. The test registry is only a deterministic collection of cases.

## Checks and commands

The suite groups checks for case integrity, profile/plugin identity, asset and
model contract, home feasibility, known FK, IK -> FK consistency, MuJoCo site
consistency, and fail-closed mismatches.

```bash
uv run pytest tests/runtime/test_robot_runtime_plugin_conformance.py -q
uv run pytest tests/runtime tests/kinematics tests/mujoco_backend tests/architecture -q
uv run python -m compileall -q src tests scripts
git diff --check
```

composition, Planar FK/IK, offline runtime smoke, viewer code, payload or
WebSocket behavior, robot assets, or hardware paths. Generic test-double
migration is Issue #387, offline smoke remains Issue #388, public Planar
exports remain Issue #389, and the related cleanup/supporting inventory is
